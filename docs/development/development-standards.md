# abcBrowser 项目开发规范

> 文档类型：项目级工程规范
> 适用项目：`alert0/abcBrowser`
> 当前目标平台：Windows x64
> 管理器基础：Prism Browser Community
> 浏览器运行时：Apostate Chromium
> 重要决策：第一阶段通过文件选择器导入用户本地已有的 `chrome.exe`，不开发内核自动下载器。
> 状态说明：本规范定义开发应遵守的规则，不代表相关功能已经实现或通过验收。

## 1. 规范目的与优先级

本规范用于约束后续 Codex 和人工开发，确保项目代码可维护、可验证、可追踪，避免“界面看起来完成、实际内核没有生效”的情况。

### 1.1 项目目标

abcBrowser 是基于成熟开源桌面浏览器管理器构建的独立桌面应用：

- 复用 Prism Browser Community 的环境管理、代理管理、进程生命周期和桌面 UI。
- 通过独立的 Apostate Engine Adapter 集成 Apostate。
- 第一阶段只支持 Windows x64。
- 支持从本地选择已有的 Apostate `chrome.exe`，检查并导入其完整运行目录。
- 为每个浏览器环境提供独立用户数据目录。
- 对运行能力、指纹配置、内核版本、导入完整性和测试结果提供真实状态。
- 先完成一个环境的真实启动闭环，再扩展批量操作和高级管理能力。

### 1.2 非目标

第一阶段不做：

- 修改或重新编译 Chromium/Apostate 内核源码。
- 内核自动下载、自动更新或在线版本发现。
- macOS、Linux 发行版。
- 重写整个桌面 UI。
- 与 AutoHW 集成。
- 尚未由 Apostate 支持或验证的指纹功能。
- 为了让界面“显得完整”而伪造能力状态。

### 1.3 规则优先级

出现冲突时，按以下顺序执行：

1. 用户已明确确认的产品决策。
2. 本规范中的安全、数据保护和真实性要求。
3. 实际使用版本的 Apostate 官方文档及真实运行行为。
4. Prism 上游实现和已有测试。
5. 本仓库的架构审查报告与开发提示词。
6. 开发者临时建议。

如果文档、代码和实际行为不一致，应记录差异并修正文档或实现；不得默默选择方便的方案。

## 2. 技术基线与版本管理

### 2.1 上游依赖

- Prism Browser Community：<https://github.com/DFarm6/Prism-Browser-Community>
- Apostate：<https://github.com/heretic-tech/apostate>

上游源码必须固定到明确的 Git commit、tag 或可验证版本，不允许无审查地追踪浮动分支作为生产构建基线。

每次更新上游，必须记录：
- 上游仓库和版本；
- 原版本与目标版本；
- 变更原因；
- 对 abcBrowser 的补丁；
- 兼容性、许可证和测试结果。

### 2.2 版本必须分开记录

不得将以下版本混为一谈：

- abcBrowser 应用版本；
- Prism 基础源码提交；
- Apostate 发布版本；
- Chromium 四段式版本；
- 本地导入内核的文件清单版本。

建议内核记录至少包含：

```text
engineId
engineRelease
chromiumVersion
platform
architecture
executablePath
sourceType
sourceVerification
manifestVersion
importedAt
```

字段应按实际数据模型命名；不得为了符合示例而破坏现有兼容性。

### 2.3 依赖管理

- 修改依赖前先确认必要性和维护状态。
- 不得无理由升级 Electron、Node.js、Vite 或其他主要依赖。
- 不得同时进行大规模依赖升级和内核集成重构。
- 锁文件必须与 package manifest 一起更新。
- 不提交 `node_modules`、编译缓存、构建产物和用户运行数据。
- CI 使用明确的 Node.js 版本及可复现的依赖安装命令。
- 不允许为了绕过类型或测试错误而随意关闭严格检查。

## 3. 架构边界

### 3.1 建议的职责分层

```text
Renderer (React UI)
  ├─ 环境管理 UI
  ├─ 内核导入与状态 UI
  ├─ 代理与兼容配置 UI
  └─ 能力提示与错误反馈
           │
           ▼
Preload / typed IPC
           │
           ▼
Electron Main Process
  ├─ ProfileStore / ProfileData
  ├─ BrowserLauncher
  ├─ KernelManager
  ├─ ProxyBridge
  ├─ ProcessInspector
  └─ ApostateEngineAdapter
       ├─ capabilities
       ├─ version inspection
       ├─ launch argument builder
       ├─ preflight validation
       └─ runtime diagnostics
           │
           ▼
Apostate Chromium runtime
```

此图用于表达职责，不要求机械照搬目录结构。实际实现应优先遵循 Prism 已有模块边界，采用最小必要改动。

### 3.2 必须遵守的边界

- Renderer 负责展示和用户交互，不直接操作任意本地文件。
- Preload 只暴露最小、明确、类型化的 IPC API。
- Main Process 负责文件对话框、路径验证、内核复制、哈希计算、进程管理和敏感操作。
- Engine Adapter 负责将通用环境配置转换成特定内核支持的启动配置。
- UI 不得自行拼接内核命令行参数。
- ProfileStore 不应承担指纹参数转换职责。
- KernelManager 不应直接读取 React 组件状态。
- 代理桥和浏览器生命周期应保持独立，避免在 UI 中管理子进程。

### 3.3 最小改动原则

- 优先复用 Prism 已有的环境模型、启动器、代理桥、进程检查与 UI。
- 不为单一需求重写成熟模块。
- 不创建两套并行的 Profile、Kernel 或 Proxy 数据模型。
- 新增抽象必须解决实际的职责隔离或测试问题。
- 上游代码如需修改，应让差异可审查、可回溯；记录 upstream commit 和本地 patch。

## 4. Apostate Engine Adapter 规范

### 4.1 单一参数入口

所有 Apostate 专属参数必须由单独的适配层生成。禁止在多个 UI 组件、IPC handler 或进程启动函数中零散拼接指纹参数。

适配器至少应提供等价于以下职责的接口：

- 返回内核能力清单；
- 校验当前环境配置；
- 构建启动参数；
- 识别当前版本支持的选项；
- 输出可理解的兼容性错误；
- 为单元测试提供纯函数式参数构造能力。

接口名称可按现有代码风格调整，但职责必须清晰。

### 4.2 参数支持证据

参数支持情况以**当前锁定版本**的 Apostate 官方文档和真实测试为准：

<https://github.com/heretic-tech/apostate/blob/main/docs/reference/switches.mdx>

不得仅凭参数名称相似、Chromium 通用行为或旧内核经验，就认定 Apostate 支持某选项。

每项指纹/运行配置应标记为：

- **supported**：文档与测试均支持；
- **unsupported**：当前内核不支持；
- **unverified**：尚未完成充分验证；
- **not-applicable**：当前平台或运行模式不适用。

状态命名可映射为项目已有的类型，但含义必须一致。

### 4.3 绝不伪装功能生效

- 保存成功不等于内核应用成功。
- 启动参数出现不等于浏览器暴露值正确。
- 浏览器进程创建成功不等于网页加载和运行时检查成功。
- 代理连接成功不等于所有 WebRTC、DNS 和地理位置行为均符合预期。
- 不支持的配置必须禁用、隐藏或明确提示。
- 不得静默将语义不同的配置映射为“近似实现”。
- 日志和 UI 必须区分配置值、传入参数、进程启动状态与实际验证结果。

### 4.4 兼容配置原则

- 使用当前 Apostate 文档中明确支持的参数。
- 对旧内核专有参数做白名单过滤，禁止透传。
- 不将 Prism 的 GPU bucket、品牌版本、操作系统版本、地理位置或渲染身份字段直接视为 Apostate 等价能力。
- 对 WebRTC 策略逐项定义语义，不得把不兼容策略静默映射成 `direct` 或 `block`。
- 不支持的强制配置应在启动前失败，并返回明确原因。
- 对所有支持字段添加参数生成测试；对关键能力添加真实浏览器运行时测试。

## 5. 本地内核导入规范

### 5.1 产品决策

第一阶段只支持用户手动选择本地 `chrome.exe`。**不得开发或依赖内核自动下载器。**

不要求用户提供 URL、Token 或额外安装服务。导入入口应通过 Electron 主进程的系统文件对话框实现。

### 5.2 导入流程

```text
用户选择 chrome.exe
        ↓
验证文件与路径
        ↓
识别可信的内核根目录
        ↓
检查版本、架构与必要资源
        ↓
复制到临时导入目录
        ↓
生成文件清单并复核
        ↓
执行安全的最小启动/诊断检查
        ↓
切换为可用内核并记录来源
```

任何一步失败都不得把该内核登记为可用。

### 5.3 完整目录原则

不能只复制 `chrome.exe`。必须根据所导入 Apostate 构建的实际目录布局，识别并复制必要 DLL、资源包、locales、ICU 数据和其他运行文件。

- 不假定所有 Chromium 构建布局相同。
- 不对整个磁盘做无边界递归搜索。
- 只允许在选定目录及明确限定的父/子目录范围内查找。
- 发现多个候选根目录时，应要求用户明确选择，不能猜测。
- 不复制无关用户文件、其他浏览器配置或用户数据。
- 导入前后检查关键文件是否齐全。
- 导入成功后记录最终可执行文件路径和内核根目录。

### 5.4 完整性与来源

- 为导入文件生成 SHA-256 清单，供后续检测意外变更。
- 明确区分“文件完整性已记录”和“官方来源已验证”。
- 用户选择的本地文件没有可信官方来源证明时，状态应为“本地导入，来源未验证”。
- 本地计算的哈希不能单独证明文件是官方发行包。
- 不得把某一版本的发行包哈希硬编码为所有版本的校验值。
- 如果将来加入官方发行包验证，应按该具体版本的官方可信清单校验，不能只信文件名。

### 5.5 原子导入与回滚

- 在临时目录中完成复制和验证。
- 验证成功后再登记或切换内核。
- 已有可用内核不得因新导入失败而损坏或被覆盖。
- 内核正在被进程使用时不得删除或覆盖其文件。
- 失败时清理临时目录并保留可诊断日志。
- 对中断、磁盘空间不足、权限错误和文件被占用进行错误处理。
- 对并发导入和同版本重复导入进行保护。

## 6. 浏览器环境与数据隔离

### 6.1 每个环境独立

每个浏览器环境必须有稳定、独立的用户数据目录，并使用独立的 `--user-data-dir`。

- 不同环境不得共享 Cookies、Local Storage、缓存或其他用户数据。
- 同一环境重启后应保留用户明确期望持久化的数据。
- 环境 ID 和数据目录映射应稳定，不能依赖可变显示名称。
- 删除环境前检查进程状态并要求用户确认。
- 内核升级、导入或切换不能自动删除环境数据。
- 数据目录迁移必须有错误恢复策略。

### 6.2 复制环境

复制环境的行为必须明确：

- 是否复制用户数据；
- 是否生成新的环境 ID；
- 是否生成新的指纹种子；
- 是否继承代理配置；
- 是否继承启动网址。

不得让复制操作意外共享同一个正在使用的数据目录。复制后的环境在启动前必须有独立的数据路径。

### 6.3 生命周期状态

环境状态至少要能区分：

- stopped / 已关闭；
- starting / 启动中；
- running / 运行中；
- stopping / 关闭中；
- error / 异常。

可沿用现有状态类型，但 UI 与持久化状态必须保持一致。不得仅凭数据库中的旧状态就断定浏览器进程仍在运行。

## 7. 代理与进程管理规范

### 7.1 代理

- 复用现有 ProxyBridge，先检查其与 Apostate 的兼容性。
- 支持范围以实际测试为准，不得将所有协议一概标记为已支持。
- 认证凭据不得写入普通日志、诊断报告或测试快照。
- 代理失败应返回明确错误，不能静默回退为直连。
- 代理配置变更后，应明确是否需要重启浏览器。
- 代理出口推导语言/时区，与浏览器 Geolocation API 模拟是不同功能，不得混为一谈。

### 7.2 进程管理

- 启动前校验内核路径、环境数据目录、参数和端口。
- 避免重复启动同一个环境。
- 进程状态需与实际 PID 和进程存活情况核对。
- 停止操作只能影响属于当前环境的进程。
- 不得根据模糊的进程名批量结束所有 Chromium 进程。
- 处理启动失败、异常退出、进程被外部关闭和应用重启恢复。
- CDP 端口默认只绑定受控的本机接口，不暴露到公网。
- 若需要调试端口，应处理端口冲突并避免将敏感连接信息写入日志。

## 8. Electron、IPC 与安全规范

### 8.1 安全默认值

- 保持 `contextIsolation: true`。
- 保持 `nodeIntegration: false`，除非已有架构存在经过审查的必要例外。
- Renderer 不直接拥有任意 Node.js 文件系统能力。
- Preload 只暴露最小的白名单 API。
- IPC handler 必须验证输入类型、长度、路径和业务状态。
- 所有路径操作应由主进程进行规范化和权限检查。
- 不把任意 shell 命令、任意可执行文件参数或任意文件读写能力开放给 UI。
- 对外部 URL、启动网址和代理地址进行合理校验。
- 不记录密码、Cookie、Authorization header、代理凭据或用户个人数据。

### 8.2 文件系统与路径

- 使用平台路径 API，不要手动拼接路径分隔符。
- 对用户选择的路径进行规范化。
- 检查目标路径是否位于预期的应用管理目录内。
- 防止路径穿越、符号链接绕过和覆盖无关文件。
- 临时文件使用唯一目录并在失败时清理。
- 对删除、覆盖和迁移操作提供明确的确认与回滚策略。

### 8.3 日志

日志应支持定位问题，但不得泄露秘密。

推荐记录：
- 时间、级别、模块；
- 内核版本和应用版本；
- 环境 ID（不含用户秘密）；
- 启动阶段；
- 错误类型和安全脱敏后的原因；
- 校验与测试状态。

不得记录：
- 代理密码；
- Cookie 或完整用户数据；
- 登录凭据；
- 含秘密的 URL 查询参数；
- 不必要的本地用户名或敏感路径。

## 9. TypeScript、React 与代码质量

### 9.1 TypeScript

- 优先使用明确的类型与判别联合类型。
- 避免新增 `any`；确实无法避免时，应缩小范围并写明原因。
- 对 IPC 的输入和返回值定义共享类型。
- 不使用类型断言掩盖未验证的外部输入。
- 文件、进程和 IPC 操作必须处理失败分支。
- 纯配置转换逻辑应尽量写成可单测的纯函数。

### 9.2 React

- UI 只展示状态，不承担内核启动参数转换或文件系统操作。
- 复用现有组件风格和设计体系。
- 异步操作需要加载状态、成功反馈和可理解的错误提示。
- 防止重复点击触发并发导入或重复启动。
- 对不支持的配置给出明确说明，不使用“已应用”一类误导性文案。
- 第一阶段以功能可用为主，不进行无关的全站视觉重构。

### 9.3 错误处理

- 对用户可恢复的错误给出下一步建议。
- 对开发诊断保留足够上下文，但先脱敏。
- 不用空的 catch block 吞掉异常。
- 不通过默认直连、默认宿主机指纹或忽略配置来掩盖失败。
- 重要失败应同时更新 UI 状态与结构化日志。

### 9.4 注释和命名

- 新增代码优先使用与项目一致的英文标识符。
- 面向用户的桌面界面使用中文。
- 注释解释原因、约束和不明显的行为，不重复翻译代码。
- 复杂兼容逻辑应链接到对应规范或官方文档。
- 删除或改变旧行为时，更新对应测试和文档。

## 10. 测试规范

### 10.1 测试层级

**单元测试**
- 启动参数构造；
- 能力清单与不支持字段；
- 版本解析；
- 路径规范化；
- 内核文件清单；
- 数据目录映射；
- WebRTC 策略兼容性。

**集成测试**
- 文件选择与 IPC；
- 本地内核导入和失败回滚；
- KernelManager 与 BrowserLauncher 的连接；
- 代理桥生命周期；
- 环境创建、关闭和重启；
- 进程归属与异常清理。

**Windows x64 端到端测试**
- 导入用户本地 Apostate 内核；
- 创建环境；
- 启动真实浏览器；
- 打开测试页面；
- 验证环境隔离；
- 关闭并重新启动；
- 验证数据持久化；
- 检查进程和代理桥是否清理。

### 10.2 测试原则

- 测试使用临时目录和可控测试数据。
- 单元测试不能随意操作用户真实浏览器目录。
- 不在测试中使用真实账户密码、Cookie 或生产代理凭据。
- 关键错误路径也必须有测试。
- 对运行时指纹的声明，必须通过浏览器内实际暴露值或其他可靠的运行时证据验证。
- 不能只检查参数数组就宣称完整指纹功能已经生效。
- 每个失败测试都要记录并处理；不能为了 CI 变绿而跳过关键测试。

### 10.3 结果标记

统一使用以下结果语义：

- **PASS**：命令实际执行并通过；
- **FAIL**：命令实际执行但失败；
- **BLOCKED**：因环境、权限或外部依赖无法执行，并记录原因；
- **NOT RUN**：尚未执行。

静态审查不能标记为运行 PASS。配置了 CI 不代表 CI 已运行。代码已提交不代表应用已构建成功。

## 11. 构建、CI 与发布

### 11.1 本地开发

- 先阅读实际 `package.json`，再使用项目中真实存在的脚本。
- 不得臆造 `test`、`typecheck` 或打包命令。
- 在修改依赖后重新检查锁文件一致性。
- 记录操作系统、Node.js、npm 与构建工具版本。
- 构建失败时保留关键错误日志并继续处理可修复的问题。

### 11.2 CI

Windows x64 CI 应逐步覆盖：

1. checkout 固定源码版本；
2. 安装规定的 Node.js；
3. 安装依赖；
4. 类型检查；
5. 单元测试；
6. 内核 Adapter 测试；
7. Windows 桌面打包；
8. 保存构建产物和日志。

由于用户可以选择本地内核，普通 CI 不应依赖开发者机器上的路径。需要真实 Apostate 二进制的测试，应使用受控测试资源或在运行环境允许时单独执行，并清楚区分与纯单元测试的结果。

### 11.3 发布门槛

发布候选版本前至少满足：

- 无已知的严重数据丢失或环境串线问题；
- 内核导入失败不会破坏已有内核；
- 启动参数不包含未支持的专有开关；
- 独立数据目录和环境生命周期测试通过；
- Windows x64 构建成功；
- 第三方许可证和版权文件已检查；
- 发布说明列出支持范围、已知问题和验证环境；
- 未经实际测试的功能不得标记为正式支持。

## 12. Git 与协作规范

### 12.1 分支

- `main`：保持可审查、文档和实现状态真实。
- 功能开发使用短期功能分支，例如 `feature/apostate-local-kernel`。
- 缺陷修复使用 `fix/<short-description>`。
- 不直接强制推送或重写共享分支历史。
- 不覆盖他人尚未提交的修改。

### 12.2 Commit

提交信息建议采用：

```text
docs: add development standards
feat: import local Apostate kernel
fix: preserve kernel after failed import
test: cover Apostate launch argument mapping
build: add Windows x64 validation workflow
```

每次提交应聚焦单一目的，避免把无关格式化、依赖升级和功能修改混在一起。

提交前执行项目适用的检查，包括：

```powershell
git status --short
git diff --check
```

随后执行真实存在的类型检查、测试和构建命令。

### 12.3 文档与代码同步

以下变更必须同步更新文档或测试：

- 新增/删除支持的指纹字段；
- 更改内核导入和校验逻辑；
- 更改用户数据目录规则；
- 更改代理行为；
- 更改启动和关闭生命周期；
- 更新 Prism/Apostate 上游版本；
- 更改构建、CI 或发布方式。

## 13. Codex 执行规范

Codex 是本项目的开发执行工具，应按以下方式工作：

1. 开始前先读取 README、本规范、集成审查报告和相关源码。
2. 先确认 Git 状态与当前分支，保护用户未提交的修改。
3. 将任务拆成可验证的小阶段，但不得只输出计划后等待批准。
4. 每次修改前阅读被修改模块及其调用方、测试和数据模型。
5. 先实现最小闭环，再扩展能力。
6. 不创建孤立的“示例 Adapter”，必须接入真实启动路径。
7. 不用文档更新代替代码实现。
8. 不用编译成功代替真实浏览器启动测试。
9. 不将未执行的测试报告为通过。
10. 不因环境受限就停止所有工作；完成当前环境允许完成的部分，并将其余项目标记为 BLOCKED。
11. 不擅自改变本规范中已确定的产品决策。
12. 完成后列出文件变更、实际命令、真实结果、commit SHA 和未解决问题。

## 14. Definition of Done（完成定义）

一个功能只有满足适用条件后才能标记完成。

### 本地内核导入

- [ ] 可以通过 UI 选择本地 `chrome.exe`。
- [ ] 根目录识别有边界且结果明确。
- [ ] 必需文件与资源已验证并完整复制。
- [ ] 生成文件完整性清单。
- [ ] 失败时不会破坏旧内核。
- [ ] UI 如实显示版本、路径、架构和来源验证状态。

### 浏览器启动

- [ ] 启动器使用 Apostate Adapter。
- [ ] 不传入未经确认的 Prism 专有参数。
- [ ] 环境有独立用户数据目录。
- [ ] 浏览器真实启动并能打开测试页面。
- [ ] 关闭、异常退出和重启流程可诊断。
- [ ] 不会误杀其他环境的进程。

### 环境隔离

- [ ] 不同环境的数据目录不同。
- [ ] 环境间 Cookies/Local Storage 不串线。
- [ ] 同一环境重启后保留预期数据。
- [ ] 复制和删除操作符合明确的数据规则。

### 质量与交付

- [ ] 对应单元测试通过。
- [ ] 相关集成测试已执行或明确标记 BLOCKED。
- [ ] Windows x64 构建已执行并记录结果。
- [ ] 文档与实际实现一致。
- [ ] 无密钥、代理凭据或用户数据进入 Git。
- [ ] 提交和推送状态如实报告。

## 15. 推荐实施顺序

1. **Phase 1：本地内核导入与最小启动。** 先使用用户本地 Apostate 内核验证完整目录导入、版本识别、启动与数据隔离。
2. **Phase 2：Apostate Engine Adapter。** 将启动参数和能力映射独立化，并补齐单元测试。
3. **Phase 3：生命周期和代理回归。** 验证多环境、代理、关闭、异常恢复和数据持久化。
4. **Phase 4：Windows CI 与安装包。** 建立可复现构建和产物留存。
5. **Phase 5：UI 清理与能力声明。** 隐藏未支持配置，确保用户能识别每个功能的真实状态。
6. **Phase 6：发布准备。** 审查许可证、版本清单、已知问题与最终验收证据。

每一阶段都必须以实际结果验收，不以“代码看起来写完”作为完成标准。
