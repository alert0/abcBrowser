# abcBrowser 完整开发任务：Prism Browser Community + Apostate 本地内核

> 用途：将本文完整交给 Codex，在 `alert0/abcBrowser` 仓库中执行实际代码集成、构建和测试。
>
> 核心目标：交付可运行的 Windows x64 桌面浏览器管理程序，而不是只生成研究报告或示例代码。

## 一、项目目标与边界

### 1.1 项目定位

- 项目仓库：[alert0/abcBrowser](https://github.com/alert0/abcBrowser)
- 桌面管理器基础：[DFarm6/Prism-Browser-Community](https://github.com/DFarm6/Prism-Browser-Community)
- 浏览器运行时：[heretic-tech/apostate](https://github.com/heretic-tech/apostate)

目标是保留 Prism Browser Community 成熟的桌面管理能力，将浏览器运行时替换为 Apostate，并把最终项目维护在自己的 abcBrowser 仓库中。不是重写浏览器内核，也不是从零开发桌面管理器。

### 1.2 已确定的技术决策

以下决定已经确定，不需要再次询问：

1. 使用 Prism Browser Community 作为桌面管理器代码基础。
2. 使用 Apostate 作为浏览器运行时。
3. 第一阶段只做 Windows x64。
4. 使用 Electron、React、TypeScript 以及上游项目实际采用的技术栈。
5. 优先复用 Prism 的环境管理、代理管理、进程管理、数据目录和内核导入功能。
6. 第一阶段不开发浏览器内核自动下载器。
7. 用户本地已经有 Apostate 的 `chrome.exe`，通过文件选择窗口导入。
8. 不要求用户重新下载 Apostate，也不要求用户填写下载 URL。
9. 不修改 Chromium 内核源码，不重新实现 Apostate 的指纹引擎。
10. 暂不开发 macOS、Linux 版本。
11. 本项目与 AutoHW 无关，不修改 AutoHW 或其他仓库。
12. 优先完成一个浏览器环境的完整启动闭环，再扩展高级功能。

## 三、第二步：实现 Apostate Engine Adapter

这是本次代码改造的核心。Prism 原有的 `launch-args.ts` 包含 Fingerprint Chromium 专用参数，不能原样用于 Apostate。

建议新建独立适配模块，具体目录可按上游结构调整：

```text
src/main/
  engines/
    apostate/
      adapter.ts
      capabilities.ts
      version.ts
      adapter.test.ts
```

不要为了追求目录结构而大规模重构其他代码。

### 3.1 统一内核接口

定义清晰的内核能力和启动接口，至少包含：

- 内核 ID、来源、版本
- 可执行文件路径
- 支持的平台和架构
- 支持的指纹参数
- 不支持的配置项
- 启动参数生成
- 启动前校验
- 启动后错误诊断

Prism 的通用浏览器启动流程应该调用适配器，而不是直接混入 Apostate 专属判断。第一阶段只有 Apostate 作为受支持运行时即可，不必提前实现多内核平台。

### 3.2 启动参数映射

以实际使用的 Apostate 版本官方文档为准：

https://github.com/heretic-tech/apostate/blob/main/docs/reference/switches.mdx

至少审查并按文档实现以下能力：

- `--user-data-dir`
- `--fingerprint`
- `--fingerprint-platform`
- `--fingerprint-hardware-concurrency`
- `--fingerprint-screen-width`
- `--fingerprint-screen-height`
- `--fingerprint-locale`
- `--fingerprint-timezone`
- `--fingerprint-webrtc-udp`

上述参数是开发检查清单，不代表可以不经核对就传给当前内核。

### 3.3 代理、窗口和扩展

继续复用 Prism 的标准 Chromium 启动能力，包括：

- 代理服务器配置
- 本地代理桥
- 窗口大小
- 独立用户数据目录
- 扩展加载
- 必要的远程调试功能
- 用户配置的启动网址

检查现有代理桥是否能把上游认证凭据正确转换给浏览器使用。不要把代理密码输出到普通日志。CDP 调试接口不得默认暴露到公网。

### 3.4 不兼容配置

逐一检查：

- Prism 专用浏览器品牌覆盖
- 操作系统版本覆盖
- 自定义渲染身份版本
- GPU bucket 或硬件模板编号
- 地理位置模拟
- WebRTC 特殊策略
- 其他专有指纹开关

对于没有确认等效实现的功能：

1. 不要生成对应的 Apostate 参数。
2. 不要静默忽略用户配置。
3. 不要把配置显示为已生效。
4. UI 可以隐藏该选项，或者显示明确的“不支持”状态。
5. 对不兼容的强制配置返回可理解的错误信息。

对于 Prism 的 `public_only` WebRTC 策略，不得未经验证就映射成 Apostate 的 `block` 或 `direct`。

第一阶段保持功能范围可控，先确保已实现的能力真实有效。

## 四、第三步：实现本地 Apostate 内核导入

**用户本地已经有 `chrome.exe`，必须允许直接选择本地文件导入。不开发自动下载功能。**

### 4.1 复用现有内核导入 UI

首先审查：

- `KernelManager.importLocal()`
- `inspectLocalBuild()`
- `normalizeBrowserSelection()`
- 浏览器可执行文件选择对话框
- 对应的 Electron IPC
- 内核列表与内核切换 UI

优先复用已有功能，不要另起一套互不兼容的内核管理系统。

界面使用中文。内核导入按钮建议显示为“导入本地内核”。

导入成功后显示：

- 内核名称：Apostate
- Chromium 版本
- 可执行文件路径或应用管理目录
- 平台与架构
- 完整性检查结果
- 导入状态

如果版本无法识别或目录不完整，应给出明确错误。

### 4.2 文件选择方式

用户选择本地的 `chrome.exe`。

使用 Electron 主进程的安全文件选择对话框。文件选择与文件系统操作应由主进程执行，Renderer 不应获得不必要的任意文件访问能力。

不能要求用户提供下载 URL、GitHub Token、内核自动下载地址或额外内核安装服务，也不能强制用户重新下载 Apostate。

### 4.3 识别内核根目录

用户选择 `chrome.exe` 后，需要确认该可执行文件所属的实际运行目录。

不能直接假设：

- `chrome.exe` 所在目录一定是完整根目录。
- 只要存在 `chrome.exe` 就可以启动。
- 所有 Chromium 构建的资源目录结构都相同。

应根据 Apostate 实际构建布局和 Prism 当前导入实现进行检查。至少识别并验证：

- `chrome.exe`
- 实际需要的 `chrome.dll`
- `chrome_elf.dll`（如果该构建需要）
- `resources.pak` 等运行资源（按实际构建检查）
- `locales` 及 ICU 数据文件（按实际构建检查）
- 其他必要 DLL 和资源目录

允许 `chrome.exe` 位于导入根目录的子目录中，但目录识别必须有边界：

1. 从所选 exe 所在目录开始检查。
2. 根据已知文件组合寻找可信运行根目录。
3. 不要无边界地向上遍历整个磁盘。
4. 如果根目录不明确，让用户重新选择或明确报告缺失文件。

不要将其他浏览器目录或用户无关文件复制进内核目录。

### 4.4 内核复制与安装

推荐流程：

```text
选择 chrome.exe
      ↓
识别内核根目录
      ↓
检查版本、架构与关键资源
      ↓
创建临时导入目录
      ↓
复制完整运行目录
      ↓
验证文件与完整性清单
      ↓
执行最小启动检查
      ↓
原子切换为可用内核
```

要求：

- 不得只复制 `chrome.exe`。
- 不能在当前内核仍被浏览器进程使用时覆盖其文件。
- 导入失败时清理临时文件。
- 保留之前可用的内核。
- 不得让不完整目录显示为导入成功。
- 复制完成后再次验证关键文件。
- 尽可能通过临时目录加原子切换实现安全安装。

如果现有 Prism 导入器已经实现其中一部分，应在现有实现上补齐缺失功能，不要无必要地全部重写。

### 4.5 版本与完整性

识别 Chromium 四段式版本，并记录 Apostate 发布版本（若可从可靠的本地元数据或来源信息确认）。

版本信息来源应按可信程度排序：

1. 可执行文件版本资源。
2. 可靠的构建元数据。
3. 用户明确提供的来源信息。
4. 文件名仅作为辅助线索。

为导入的文件生成 SHA-256 清单。

本地文件计算出来的 SHA-256 只能用于后续完整性检查，不能单独证明文件是官方发行包。如果用户的本地文件没有官方包的来源证明，界面应显示“本地导入，来源未验证”，不要伪装成已验证的官方发行包。

本阶段不需要实现自动下载、自动更新和 Release API。

## 五、第四步：接入 Prism 环境管理

保留 Prism 已有的环境管理界面和数据结构。第一阶段至少实现一个环境的完整生命周期：

1. 创建环境。
2. 设置环境名称。
3. 设置启动网址。
4. 保存指纹种子和受支持的配置。
5. 保存代理配置。
6. 为环境创建独立用户数据目录。
7. 启动浏览器。
8. 关闭浏览器。
9. 重新启动浏览器。
10. 删除环境前检查浏览器进程并要求用户确认。

### 5.1 数据目录隔离

每个环境必须使用独立的 `--user-data-dir`。

要求：

- 环境之间不能共享 Cookie 和本地存储。
- 环境之间不能共享会被 Chromium 错误复用的用户配置目录。
- 同一环境重启后保留登录状态和用户数据。
- 复制环境时，按照产品规则决定是否生成新的指纹种子。
- 不能因为内核切换而删除现有环境数据。
- 不能在环境仍运行时随意迁移或覆盖数据目录。

检查现有 `profile-store.ts`、`profile-data.ts` 和启动器，尽量保留原有数据模型。

### 5.2 启动和关闭

检查 `browser-launcher.ts` 的完整生命周期。

要求：

- 正确解析 Apostate 可执行文件路径。
- 生成并验证启动参数。
- 正确设置用户数据目录。
- 检查启动失败。
- 保存实际进程 PID 和环境状态。
- 关闭浏览器后更新环境状态。
- 避免重复启动同一个环境。
- 避免关闭一个环境时误杀其他浏览器进程。
- 异常退出后可以恢复环境状态。
- 错误日志能够帮助定位启动失败原因。

不要仅凭进程创建成功就认定浏览器已经启动成功。至少验证进程存活；如果现有实现支持可靠的 CDP 检查，可进一步验证浏览器已准备好。
